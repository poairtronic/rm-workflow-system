# PHASE 10 — USER MANAGEMENT ARCHITECTURE & RECONCILIATION

## 1. OBJECTIVE
The objective of Phase 10 Objective A is to finalize and reconcile the User Management & Security model for RMRIT, ensuring that user authentication, identity rules, password security, role-based access control (RBAC), and actor traceability align 100% with the authoritative requirements baseline without introducing unapproved user attributes or workflows.

---

## 2. CURRENT USER ARCHITECTURE
- **Framework**: NestJS (`UsersModule`, `AuthModule`, `RolesModule`).
- **Entity**: `User` mapped to PostgreSQL table `users`.
- **Authentication**: JWT Bearer token authentication via `JwtAuthGuard` and `AuthService`.
- **Authorization**: Role-based guard (`RolesGuard`) evaluating `@Roles(...)` metadata annotations against verified JWT token claims.

---

## 3. USER ENTITY
```typescript
export class User {
  id: string; // Primary key (UUID v4)
  name: string; // Full user name (varchar 100)
  email: string; // Unique normalized email (varchar 150)
  passwordHash: string; // Hashed password string (varchar 255)
  roleId: string; // Foreign key to roles table
  role: Role; // Relational join to Role entity
  department?: string; // Optional department (varchar 100)
  isActive: boolean; // Account status flag (default: true)
  createdAt: Date; // Creation timestamp
  updatedAt: Date; // Modification timestamp
}
```
*Note: Fields like employee ID, biometric data, profile photos, salary, or approval hierarchies are OUT OF SCOPE and NOT present in the core model.*

---

## 4. USER IDENTITY & NORMALIZATION
- **Primary Key**: Internal UUID `id` generated by PostgreSQL / TypeORM.
- **Unique Identifier**: `email` is strictly unique (`@Index({ unique: true })`).
- **Normalization**: User emails are converted to lowercase and trimmed of leading/trailing whitespace (`email.toLowerCase().trim()`) upon registration and login validation.
- **Database Authority**: PostgreSQL unique constraints enforce email uniqueness as the absolute authority.

---

## 5. PASSWORD SECURITY
- **Hashing Standard**: Passwords hashed using `bcrypt` (work factor 10).
- **Plaintext Storage**: Plaintext passwords are NEVER stored in the database.
- **Exposure Protection**: `passwordHash` is excluded from all standard user API responses, logs, and token payloads.
- **Verification**: Executed strictly in `AuthService.validateUserCredentials` using `bcrypt.compare`.

---

## 6. USER LIFECYCLE (ACTIVE / INACTIVE)
- **Active User (`isActive = true`)**:
  - Allowed to authenticate (`AuthService` validates `user.isActive`).
  - Allowed to perform role-authorized backend transactions.
- **Inactive User (`isActive = false`)**:
  - Cannot log in (`AuthService` throws `401 Unauthorized: User account is inactive`).
  - Cannot issue tokens or perform new business operations.
  - **Traceability Protection**: Inactive user records are NEVER deleted from the database (`HARD DELETE RESTRICTED`) to preserve historical auditability in `StockTransaction.createdById` and `AuditLog.userId`.

---

## 7. ROLE MODEL
RMRIT strictly supports the 6 authoritative roles:
1. `ADMIN` — System administrator & master data manager.
2. `DESIGNER` — Authors RM Material Lists.
3. `STORES` — Manages physical stock IN, Stores Issue, and inventory verification.
4. `PRODUCTION` — Receives, consumes, and returns production materials.
5. `SENIOR_MANAGER` — Observer & Analytics role (Read-only / Dashboards).
6. `GENERAL_MANAGER` — Observer & Analytics role (Read-only / Dashboards).

> **CRITICAL RECONCILIATION RULE**: `SENIOR_DESIGNER` is completely absent from active enums, guards, DTOs, seed data, and tests.

## 9. AUTHENTICATION FLOW RECHECK
```
Client Request (Login)
       │
       ▼
AuthController.login(LoginDto)
       │
       ▼
AuthService.validateUserCredentials(email, pass)
       │
       ├── 1. Query User by normalized email
       ├── 2. Check if User exists (401 if missing)
       ├── 3. Check if User.isActive == true (401 if inactive)
       └── 4. Verify password with bcrypt.compare (401 if mismatch)
       │
       ▼
Generate JWT Token (sub: userId, role, roles, email)
       │
       ▼
Return Access Token + User Info Envelope
```

---

## 10. ACTOR TRACEABILITY
- **Security Rule**: Client-supplied `createdById`, `actorId`, or `userId` in API payloads are strictly IGNORED by backend controllers and services.
- **Enforcement**: `JwtStrategy` validates the Bearer token, populating `req.user`. Controllers extract `req.user.sub` as the authoritative actor ID for all inventory transactions and audit logs.

---

## 12. USER API CONTRACT (CONCEPTUAL / FOUNDATION)
- `POST /api/auth/login` — Authenticate user & return JWT token.
- `GET /api/users/profile` — Get current user profile.
- `GET /api/users` — List users (Admin / Management only).
- `POST /api/users` — Create new user (Admin only).
- `PATCH /api/users/:id/deactivate` — Deactivate user (Admin only).
- `PATCH /api/users/:id/reactivate` — Reactivate user (Admin only).
