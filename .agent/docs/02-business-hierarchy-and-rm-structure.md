# RMRIT — Business Hierarchy & RM Material Structure

## Core Hierarchy
```
CUSTOMER → PO/JOB → SC-001 / SC-003 / SC-005 (siblings) → RM WORKFLOW (per SC)
```
- **PO** already exists in another company system — RMRIT does **not** create the real PO, it only *records* the PO number/reference (`External System → PO-001 → RMRIT records PO number`).
- **SC numbers are manually entered** — they originate from the company's existing process, not generated by RMRIT.
- A PO can have many SCs. An SC can have its own RM request, and multiple RM requests can exist against the same SC over time (e.g. additional material later).
- Admin can manage PO information when necessary.

## RM Request Types (Designer chooses one)
**Option A — RM for individual SC**
```
PO-001 → SC-001 → RM List
```
**Option B — RM for entire PO** (multiple SC sections in one request flow)
```
PO-001 → SC-001 → RM List
       → SC-003 → RM List
       → SC-005 → RM List
       → [+ Add SC] (creates another SC section with its own material rows)
```
No practical limit on number of SC sections beyond reasonable system constraints.

## RM Material Row — Fields
| Field | Required |
|---|---|
| Material Grade | Yes |
| Size | Yes |
| Quantity | Yes |
| Length | Yes, where applicable |
| Width | Optional |
| Thickness | Yes, where applicable |
| Diameter | Yes, where applicable |
| Weight | Optional |
| Remarks | Recommended |

Example grades: `EN31`, `OHNS`, `MS`. Example sizes: `Ø115×25`, `Ø105×25`, `Ø150×15`, `Ø20×75`.

## Key Design Decision: Flexible Dimensions
**Do not force every dimensional field to be populated.** Different material shapes use different subsets of fields:

```
Material: EN31          Material: MS
Size: Ø115×25            Size: 100×50×10
Diameter: 115             Length: 100
Length: 25                 Width: 50
Width: NULL                 Thickness: 10
Thickness: NULL              Diameter: NULL
Weight: NULL
Qty: 1
```
The system supports different material forms without making irrelevant fields mandatory. Each row is explicitly tied to its PO and SC.

## Original RM Must Remain Intact (important architectural rule)
If Production later needs more of a material already on the original RM, the app must **never edit the original requested quantity**. Instead it records an **Additional Requirement** as a separate transaction:

```
Original RM: EN31 Ø50×25 Qty 10
Production later needs: EN31 Ø50×25 Qty 5

WRONG:  Original quantity changed 10 → 15
RIGHT:  Original Requirement = 10
        Additional Requirement = 5
        Total Material Flow = 15
```
This lets management understand *why* additional material was needed. A completely new material (not on the original RM at all) is always treated as an **Additional Material Request**, never as an edit to the original approved RM.
