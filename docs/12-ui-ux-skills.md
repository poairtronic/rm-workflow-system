# RMRIT — 10 UI/UX Development Skills

RMRIT is internal manufacturing workflow software, not a consumer SaaS product. Every screen should look and feel like it was built by people who understand a shop floor — not generated by an AI trying to look impressive. These 10 skills are the standard every screen is held to.

## 1. Human-Centered Workflow Design (`human-centered-workflow-ui`)

Design around what the employee needs to **do next**, not around database tables or feature lists. Before building a screen, ask: _"What is the user trying to accomplish here?"_

**Bad (AI-style):** equal-weight stat cards (Total PO / Total SC / Materials / Pending / Completed) plus generic "Recent Activities" and "Analytics" blocks — everything looks equally important, nothing tells the user what to do.

**Good:** a Stores screen that leads with the SC, shows material-by-material availability, and ends in one clear call to action:

```
MATERIAL ISSUE
PO-100 / SC-003
Customer: ABC Industries · Product: Air Gauge

Material Status
EN31   Ø110×35   Required 2   ✓
OHNS   Ø70×18    Required 1   ✓
MS     Ø150×15   Required 1   ⚠

3 materials available · 1 material pending
                    [Issue Available]
```

## 2. Information Hierarchy (`information-hierarchy`)

Control what the user notices first, second, third. For RMRIT the priority order is almost always:

```
SC Number → Current Status → Required Action → Material Status → Details → History
```

...never: big decorative title → stat cards → icons → charts.

**Bad:**

```
SC-003
[Pending] [PO-100] [ABC Industries] [4 Materials] [Created 02/09/2026]
[View]
```

**Good:**

```
SC-003                         PENDING STORES ISSUE
PO-100 · ABC Industries · Air Gauge

Material
EN31   Ø110×35   2   AVAILABLE
OHNS   Ø70×18    1   AVAILABLE
MS     Ø150×15   1   PENDING

Next action: Issue the available materials
                    [Issue Materials]
```

**Instruction:** SC number, workflow status, and next required action must dominate the screen. Secondary metadata stays visually subordinate. Never give every field equal visual weight.

## 3. Manufacturing-Domain UI Language (`manufacturing-domain-ui`)

The app must speak the shop's language, not generic SaaS language. Use PO, SC, RM Material, Material Grade, Size, Qty, Available, Pending, Issued, Received, Consumed, Returned, Additional Requirement, Production Completed.

| Generic SaaS        | Use instead          |
| ------------------- | -------------------- |
| Create New Request  | Create RM List       |
| Request Status      | Material Status      |
| Task Completed      | Production Completed |
| Transaction History | Material Movement    |

Example table that "immediately feels like internal manufacturing software":

```
RM MATERIAL STATUS
Material    Grade   Size      Required  Issued  Pending
Round Bar   EN31    Ø110×35      2         2       0
Round Bar   OHNS    Ø70×18       1         1       0
MS          MS      Ø150×15      1         0       1
```

## 4. Workflow State Visualization (`workflow-state-ui`)

Status design matters more than dashboards here — this is fundamentally a workflow system. Use one consistent state ladder end-to-end:

```text
DRAFT → SUBMITTED / STORES PENDING → PARTIALLY ISSUED
→ ISSUED → RECEIVED → IN PRODUCTION → ADDITIONAL REQUEST → COMPLETED
```

Show current stage as a clear progress trail (`● Design ─ ● Stores ─ ● Production ─ ◉ Completed`), with the current stage visually distinct.

**Never rely on color alone** for status — always pair a symbol with the label:

```text
✓ Available     ⚠ Partially Available     ! Pending
↻ Additional Request     ✓ Completed
```

## 5. Realistic Data Design (`realistic-data-design`)

Never use lorem ipsum, "John Doe," "Product A," "Material 01," or other meaningless placeholders anywhere in the shipped UI. Use realistic manufacturing data — real-sounding customer names, real grades (EN31, OHNS, MS), real sizes (Ø110×35), and plausible timestamped transaction history:

```text
02 Sep 09:32  Design submitted RM list
02 Sep 09:35  Stores notified
02 Sep 11:15  Stores issued 2 × EN31
02 Sep 11:16  Stores issued 1 × OHNS
02 Sep 11:17  MS Ø150×15 pending
```

This is what makes the UI read as a real operational system rather than a demo.

## 6. Progressive Disclosure (`progressive-disclosure-ui`)

Don't show everything at once — especially material history. Three levels, each opened deliberately by the user:

**Level 1 (summary):**

```
SC-003
Production Status: IN PRODUCTION
Materials: 4 / 4 received
Consumed: 320 kg · Returned: 80 kg · Additional Request: 1
```

**Level 2 (`View Material Movement`):**

```
INITIAL ISSUE — Issued: 500 kg
PRODUCTION — Consumed: 400 kg · Returned: 100 kg
ADDITIONAL REQUEST — Requested: 50 kg · Issued: 50 kg
```

**Level 3 (`View transaction details`):** the full timestamped transaction log (see skill 7).

## 7. Transaction & Audit Timeline Design (`audit-trail-ui`)

Every material movement must be traceable — so never collapse a lifecycle down to `Status: Completed`. Show the actual timeline, one event per entry, with who/what/when:

```
SC-003 — MATERIAL HISTORY
09:10  DESIGN SUBMITTED · Raghav · RM list submitted
  ↓
10:05  SENIOR VERIFIED · Senior Manager · No changes
  ↓
11:20  MATERIAL ISSUED · Stores · EN31 20kg, OHNS 10kg
  ↓
12:00  MATERIAL RECEIVED · Production · 30 kg received
  ↓
16:45  MATERIAL RETURNED · Production · 8 kg returned
  ↓
17:00  PRODUCTION COMPLETED · Production · Completed with remarks
```

This is the screen that answers "what happened to the material?" instantly — it should never require piecing together multiple tables.

## 8. Form UX Engineering (`business-form-ux`)

The RM form is one of the most important screens — never a giant form with 20 unrelated fields visible at once. Build it as a guided sequence:

```
Step 1: PO Number + RM List Type (○ Single SC  ● Entire PO) → [Continue]
Step 2 (if Entire PO): SC list, each as a card with "N materials" + [Edit], plus [+ Add SC]
Step 3: Add Material — Grade, Size, Qty required; Weight/Width/Thickness/Diameter optional
         → [Add Material]
```

After adding, materials collapse into a compact row list with `[Edit] [Delete]` — never 30 fields permanently on screen:

```
EN31 | Ø110×35 | Qty 2 | [Edit] [Delete]
OHNS | Ø70×18  | Qty 1 | [Edit] [Delete]
MS   | Ø150×15 | Qty 1 | [Edit] [Delete]
```

## 9. Exception-First Design (`exception-first-ui`)

Normal cases need minimal visual attention; exceptions need to jump out — this is the single most important skill for Stores and Production screens. Standard exception markers:

```
⚠ Material Pending     ⚠ Partial Issue     ⚠ Additional Requirement
⚠ Excess Material      ⚠ Material Returned  ⚠ Production Error
```

Example — normal row vs. exception row:

```
EN31   Ø110×35   Required 2   Issued 2                 ✓
MS     Ø150×15   Required 4   Issued 2   ⚠ PENDING 2
```

An additional material request should read as something that needs attention, not a routine line item:

```
ADDITIONAL MATERIAL REQUEST — SC-003
Material: EN31 · Required: 20 kg · Additional: 5 kg
Reason: Manufacturing error
                         [Review Request]
```

The user should immediately understand: _something needs my attention._

## 10. Visual Restraint & Anti-AI-UI (`anti-ai-ui`)

This is the skill that keeps RMRIT from looking like a generic AI-generated dashboard demo. Apply it strictly.

**Avoid:** excessive rounded cards · gradient backgrounds · giant hero sections · excessive shadows · random colorful icons · a wall of 10 dashboard stat cards · huge display typography · decorative illustrations · unnecessary animation · glassmorphism · purple/blue "AI" gradients · every button styled as a primary button.

**Prefer:** clean tables · strong typography · clear spacing · subtle borders · a restrained, consistent color palette tied to status semantics · dense-but-readable data · clear, singular primary actions per screen · logical grouping · designed empty/loading/error states.

**Bad:**

```
╭─────────────────────────────╮
│ ✨ MATERIAL MAGIC            │
│      500 KG                  │
│      ───────                 │
│      Material                │
│      [Explore →]             │
╰─────────────────────────────╯
```

**Good:**

```
MATERIAL SUMMARY
Issued          500 kg
Consumed        400 kg
Returned        100 kg
────────────────────────
Balance           0 kg
Material status:  ✓ Closed
```

## Mandatory: The "Real Employee Test"

Before the agent considers **any** page finished, it must simulate an actual employee using it under a realistic scenario.

**Example — Stores page, PO-100/SC-003 with 5 RM items (3 available, 2 pending).** The agent must confirm the user can immediately answer, without navigating elsewhere:

```
✓ Which SC am I on?
✓ Which materials are required?
✓ Which are available?
✓ Which are pending?
✓ What can I issue right now?
✓ What remains after that?
✓ When was this request received?
✓ What have I already issued?
✓ What should I do next?
```

**If the employee would need to hop across multiple screens to answer these, the screen has failed the test and is not done** — regardless of whether the underlying data/API work is complete.

## Recommended Build Order

Each phase must pass the Real Employee Test before moving to the next:

```text
Phase 1  Design System
Phase 2  Login + Navigation
Phase 3  Design RM Workflow
Phase 4  Stores Workflow
Phase 5  Production Receipt
Phase 6  Consumption / Return
Phase 7  Additional Material Request
Phase 8  SC Completion
Phase 9  Monitoring & Analytics Dashboard
```

This build order is UI-focused and complements — not replaces — the backend-oriented phase list in `10-dev-phases-and-testing.md`; the two should be worked roughly in parallel per phase (backend transaction/endpoint for a workflow step, then the screen that uses it, then the Real Employee Test on that screen).
